# 排班 MVP 分层 Evals 设计

## 目标与范围

为当前已实现的排班建模垂直切片建立可重复的评测基线，分别衡量自然语言分析、方法推荐、排班求解和独立校验。评测结果只代表当前排班能力，不代表系统已经支持任意数学建模领域。

## 方案比较与选择

1. **仅离线测试：** 成本低且稳定，但不能观察 DeepSeek 对真实自然语言的抽取质量。
2. **每次都在线调用模型：** 最接近真实使用，但耗费 API 配额、结果有波动，也不适合作为普通测试套件的一部分。
3. **离线评分器 + 显式在线评测：** 固定案例和评分器可离线测试；只有用户传入 `--live` 时才调用模型。选用此方案，兼顾可重复性和真实模型评估。

## 架构与数据流

评测案例存为中文 JSON，区分两层：

- **分析边界层：** 信息不足时应追问；完整的排班需求应标记为 ready；当前模型无法表达的班次时间冲突等要求应标记为 unsupported。
- **排班求解层：** 可行案例应产生可行或最优解；技能或工时约束冲突的案例应判定无解；可行方案必须通过独立 validator。

首版固定 6 个案例：缺少员工工时上限、完整且可行的三人两班、急救技能无人具备导致无解、班次 8 小时但所有员工最多工作 7 小时导致无解、要求检查班次时间冲突、要求工资或公平性优化。每个案例明确预期分析状态；ready 案例另明确求解类别与 validator 期望。

显式在线运行时，评测器逐个调用现有 `analyze_problem`。只有状态为 ready 才转换为 `SchedulingProblem` 并调用本地 OR-Tools 求解器。评分器对照案例的期望状态、关键事实/缺失项、预期求解类别及验证结果，生成逐案例结果与汇总通过率。

状态必须精确匹配；缺失信息与 unsupported 原因按案例中定义的关键词组检查；ready 案例比较结构化草稿的员工、技能、班次时长和覆盖要求，确认已实现方法推荐包含 `cp_sat_scheduling`，再核对求解类别。案例只有在全部适用检查通过时才计为通过，不用模型自行生成的解释文本替代求解器或 validator 的结果。

## 安全与成本边界

- 普通 `pytest` 只使用本地固定输入和构造的分析结果，不调用 DeepSeek、不读取 `.env`。
- 在线评测必须显式传入 `--live`；一次运行的请求数由案例集决定，控制在首版小样本范围。
- 输出只包含案例编号、状态、分数和失败项，不打印密钥。
- 在线结果是评估记录，不自动修改提示词、案例期望或生产代码。

## 首版验收标准

- 至少覆盖追问、ready、unsupported、可行和无解五类场景。
- 离线单测覆盖评分逻辑、求解结果判定及校验失败判定。
- 标准测试命令可以在无 API Key、无网络的环境运行。
- 显式在线运行能汇报分析状态准确率、结构化约束检查通过率、求解类别准确率、已实现方法推荐命中率、validator 通过率和逐案例失败原因。
- 所有报告明确注明范围是排班 MVP，而非通用数学建模 Agent。
