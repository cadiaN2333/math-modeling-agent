# 最小费用网络流领域适配器设计

## 目标

在现有员工排班与连续单目标线性规划之后，增加第三个真实求解领域：整数单位的最小费用网络流。首个端到端案例采用仓库向门店配送，Agent 从自然语言提取节点供需、路线容量与单位费用，调用 OR-Tools 求解，并由独立 validator 复核流量守恒、容量和总费用。

## 本期范围

- 支持有向图上的单商品最小费用流。每个节点具有整数净供给量：正数表示供给，负数表示需求，零表示中转节点。
- 每条有向边具有起点、终点、整数容量和整数单位费用；每单位流量按指定整数流量单位计量。运输问题是其中的二部图特例：仓库为供给节点、门店为需求节点，配送路线为边。
- 求解目标固定为满足全部节点供需的最小总费用。总供给与总需求不平衡、路线容量不足或网络不连通时，返回不可行状态；本期不允许部分满足需求。
- 数量必须是整数流量单位（如件、箱）。费用按整数费用单位表示；若输入使用小数货币，应转换成明确的最小货币单位，例如 2.35 元/箱表示为 235 分/箱，并保留单位说明。
- 支持一般中转节点和任意有向路线；不支持多商品流、最大流、部分供需的最小费用最大流、车辆路径/时间窗、整数规划以外的连续流量等问题。

## 方案比较与选择

1. **只做仓库—门店运输矩阵：** 输入简单、易展示，但难以自然表达中转仓和多段路线。
2. **通用单商品最小费用流，运输作为首个实例：** 用节点供需和有向边容量/费用描述模型；稍多一层图概念，但同一适配器可覆盖运输与一般网络流。本期采用。
3. **使用 GLOP 将流量建成连续 LP：** 与已有 LP 求解器一致，能表示小数流量；但不能保证整数发运单位，也会与 LP 领域重复。

本期采用方案 2。官方 OR-Tools 最小费用流接口正是通过有向边、容量、单位费用和节点供需定义模型，并要求供需平衡且容量足以运送全部供给；底层数量与费用类型为 64 位整数。[OR-Tools 最小费用流指南](https://developers.google.com/optimization/flow/mincostflow) [SimpleMinCostFlow 类型与约束](https://github.com/google/or-tools/blob/stable/ortools/graph/min_cost_flow.h)

## 结构化分析格式

扩展 `ProblemAnalysis.problem_family`，新增 `minimum_cost_flow`；同时增加固定、必填、非 Optional 的 `minimum_cost_flow_draft`，继续保留排班和 LP 草稿字段，以维持 Structured Outputs 的稳定 JSON Schema。

- `minimum_cost_flow_draft.nodes`：节点编号、名称、带符号整数净供给量。
- `minimum_cost_flow_draft.arcs`：边编号、起点编号、终点编号、整数容量、整数单位费用。
- 草稿另含 `flow_unit` 与 `cost_unit`，明确流量和费用单位。非活动领域使用固定空形状：节点与边列表为空，两个单位字段均为 `not_applicable`。
- ready 且领域为 `minimum_cost_flow` 时，只允许最小费用流草稿非空；排班和 LP 草稿必须为空。需要澄清或不支持时所有领域草稿为空。
- 仅提取用户明确提供的数据，不推断路线、容量、供给、需求或费用；价格精度不能无损转换成整数费用单位时，先追问。

## 模块与数据流

- `analysis_agent.py`：更新问题族与提示词、固定 draft Schema、跨领域草稿互斥校验，并新增 `to_minimum_cost_flow_problem()` 转换。
- `models.py`：增加节点、路线和网络流问题输入模型；校验节点/边编号唯一、路线端点有效、容量非负、供需与费用均为整数。
- `analysis_agent.py`：校验节点与路线草稿引用有效；非活动网络流草稿使用固定空形状，ready 时与其他领域草稿互斥。
- 新增 `min_cost_flow_solver.py`：使用 `ortools.graph.python.min_cost_flow.SimpleMinCostFlow` 建立节点和路线，映射为稳定状态，只有最优状态才返回各路线流量与总费用。
- 新增 `min_cost_flow_validator.py`：不依赖求解器状态，逐边检查 `0 <= flow <= capacity`，逐节点检查流出量减流入量等于净供给，并独立重算总费用。
- 新增 `min_cost_flow_agent.py`：检索 HMML 最小费用流方法，编排求解和 validator，保持与其他领域一致的 `solver_result`、`validation_report`、`method_recommendations` 顶层结构。
- `cli.py`：按 `problem_family` 路由到排班、连续 LP 或最小费用流适配器；澄清和 unsupported 仍不得启动求解器。
- `data/hmml.json`：在运筹优化网络流子领域新增 `minimum_cost_flow` 方法卡，求解器标记为 OR-Tools SimpleMinCostFlow、状态标记为“已实现”；多商品流和最大流仍为未实现候选。
- `evals/cases.json`：把运输网络流边界案例升级为可求解的仓库—门店运输案例，并增加一个容量不足或供需不平衡的不可行案例；整数/非线性、多商品等边界仍应为 unsupported。

## 首个端到端案例与验收

流量单位为箱，费用单位为元/箱：仓库 W1 供给 20 箱，W2 供给 30 箱；门店 S1 需求 25 箱，S2 需求 25 箱。路线及（容量，单位费用）为：W1→S1（20，2）、W1→S2（20，4）、W2→S1（25，3）、W2→S2（30，1）。预期最优总费用为 80，最优路线流量为 W1→S1 发 20、W2→S1 发 5、W2→S2 发 25，其余路线发 0。

验收要求：结构化草稿与期望数据一致；求解状态为 `OPTIMAL`；路线解与总费用符合上例；validator 报告有效。不可行案例必须返回 `INFEASIBLE` 且不伪造路线流量或验证报告。

## 错误处理与安全边界

- 不平衡供需、容量不够或缺少可行路径均明确作为 infeasible，不自动增加虚构供给、需求或高成本虚拟边。
- 费用或容量超出 OR-Tools 安全范围时返回明确错误状态，不读取或生成伪造解。
- 用户要求不可整除的流量单位时，追问最小可计量单位；不得把连续流量四舍五入成整数。
- 多商品流、最大流、部分满足需求、车辆路径与时间窗约束必须标记 unsupported，并说明具体原因。
- 普通 pytest 使用固定构造的分析结果，不调用 DeepSeek；真实模型抽取只通过显式 `--live` Evals 验证。
